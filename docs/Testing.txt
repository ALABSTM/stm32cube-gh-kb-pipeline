Si le RAG ST fait lui-même le chunking, il ne faut pas lui donner les fichiers déjà chunkés. Le bon niveau d’entrée est le niveau document enrichi, donc les fichiers docs V2, pas les fichiers chunks.

À passer en entrée:

docs_issues_stm32cubeh7_v2.json
docs_files_stm32cubeh7_v2.json
Pour H5, l’équivalent:
docs_issues_stm32cubeh5_v2.json
docs_issues_stm32cubeh5_v2_sim.json
Le principe est simple:

raw_* : trop brut, trop de bruit, pas prêt pour ingestion.
clean_* : texte nettoyé mais pas assez enrichi.
docs_*_v2 : meilleur compromis, car tu gardes le texte complet par document + les métadonnées utiles.
chunks_*_v2 : inutile si ST re-chunke déjà, et même risqué car tu fais un double chunking.
La meilleure recommandation est donc:

utiliser docs_issues_*v2.json et docs_files*_v2.json comme source documentaire;
si ST accepte des métadonnées, injecter chaque objet du JSON comme un document avec son clean_text comme contenu principal et les autres champs comme metadata;
si ST n’accepte pas bien un gros JSON, alors convertir chaque document V2 en un fichier texte ou markdown individuel avant import, mais toujours à partir de docs_*v2 et non de chunks*.
Je ne recommande pas de passer directement docs_issues_stm32cubeh5_v2_sim.json ou docs_issues_stm32cubeh7_v2_sim.json sauf si tu veux absolument conserver related_issue_ids. Sinon la version non sim suffit. La version sim est utile si le système ST sait exploiter une metadata de voisinage sémantique.

Détail de l’évaluation et validation qualité

Objectif global
Cette phase ne sert pas encore à mesurer la performance finale d’un vrai moteur RAG avec embeddings. Elle sert à valider que le preprocessing produit une base documentaire cohérente, exploitable, et raisonnablement recherchable.
Elle répond à deux questions:

Est-ce que les documents enrichis ont des distributions plausibles ?

Est-ce qu’une recherche lexicale simple retrouve déjà des documents pertinents ?

Validation statistique des issues
Script: test_stats_issues_v2.py

Ce script charge docs_issues_stm32cubeh7_v2.json ou l’équivalent selon le repo, puis calcule des distributions sur:

layer
severity
issue_kind
board
component
Ce que le script mesure exactement:

layer: combien d’issues sont classées HAL, LL, Middleware, CubeMX, Other.
severity: combien d’issues sont low, medium, high.
issue_kind: combien sont bug_report, usage_question, configuration_help, other.
board: quelles cartes sont les plus détectées.
component: quels composants sont les plus détectés.
Pourquoi c’est utile:

vérifier que les heuristiques de classification ne produisent pas une distribution absurde;
repérer les champs sous-détectés;
voir si certaines classes dominent de manière anormale.
Exemples d’interprétation:

Si presque tout tombe dans Other pour layer, la règle detect_layer est trop faible.
Si presque tout est high pour severity, les mots-clés high sont probablement trop agressifs.
Si board est presque toujours vide, la regex de détection des cartes doit être enrichie.
Si component retourne surtout ETH ou USB alors que beaucoup d’issues parlent ADC/UART/CAN, il faut ajuster les mots-clés.
Ce que cette validation prouve:

la qualité structurelle des métadonnées issues avant indexation.
Ce qu’elle ne prouve pas:

la qualité finale des réponses générées par le RAG.
Validation statistique des fichiers
Script: test_stats_files_v2.py
Ce script charge docs_files_stm32cubeh7_v2.json, puis calcule:

file_type
board
component
nombre total de docs
nombre de docs valides
Ce que le script vérifie:

la répartition entre root_readme, project_readme, release_notes, doc_readme, other;
la part de documents retenus après filtrage is_valid;
la qualité de détection board/component sur les docs fichiers.
Points d’analyse importants:

Si is_valid est trop bas, le seuil minimal de longueur est peut-être trop strict.
Si presque tout est classé root_readme ou other, la logique detect_file_type dans clean_files.py est à revoir.
Si board est bruité, cela peut venir du fait qu’un README liste plusieurs cartes et que la première occurrence capturée n’est pas la plus représentative.
Si component est faux sur les README généraux, c’est normal dans une certaine mesure, car les docs globaux citent beaucoup de composants différents.
Ce que cette validation confirme:

le corpus fichiers est correctement structuré avant ingestion RAG.
Validation retrieval par TF-IDF sur les issues
Script: test_tfidf_search_issues_v2.py
Fonctionnement:

charge docs_issues_stm32cubeh7_v2.json;
garde seulement les documents is_valid = true;
construit un index TF-IDF sur:
titre + clean_text
pour une requête utilisateur, calcule la similarité cosinus;
retourne les top résultats avec:
issue number, title, layer, severity, board, component, github_url.
Pourquoi TF-IDF est utilisé ici:

ce n’est pas le moteur final;
c’est un test simple, rapide, interprétable;
s’il échoue à retrouver des résultats plausibles, il y a souvent un problème plus fondamental dans le corpus.
Ce qu’on évalue concrètement:

une requête sur ADC + DMA doit remonter des issues ADC proches;
une requête sur Ethernet, lwIP, FreeRTOS, USB, UART doit faire remonter des documents du bon composant ou de la bonne couche;
une requête sur CubeMX doit remonter des issues classées CubeMX.
Exemples de questions de test:

ADC DMA configuration invalid
Ethernet no communication STM32H7
FreeRTOS deadlock USB
CubeMX generated code problem
UART warning cast align
Critère qualitatif attendu:

dans les 3 à 5 premiers résultats, on doit voir plusieurs documents clairement reliés à la requête;
les métadonnées affichées doivent être cohérentes avec le sujet remonté.
Ce que ce test valide:

le texte nettoyé contient bien le signal sémantique minimal;
le filtrage is_valid n’a pas supprimé des documents importants;
les documents enrichis sont déjà récupérables avant embeddings.
Validation retrieval par TF-IDF sur les fichiers
Script: test_tfidf_search_files_v2.py
Fonctionnement:

charge docs_files_stm32cubeh7_v2.json;
conserve seulement les fichiers valides;
construit un texte indexé sous la forme:
path + file_type + clean_text
calcule les top résultats pour une requête donnée.
Pourquoi c’est intéressant:

pour les fichiers, le chemin et le type de document ont beaucoup de valeur;
une requête comme Ethernet example, USB host readme, Release Notes ADC doit déjà retrouver les bons fichiers ou README.
Ce qu’on regarde dans les résultats:

le path doit être cohérent avec le sujet recherché;
le file_type doit être logique;
l’extrait affiché doit confirmer que le contenu correspond.
Exemples de requêtes utiles:

ethernet example nucleo h743
usb host project readme
release notes fdcan
freertos examples stm32h7
adc documentation
Comment présenter cette phase dans ton rapport
Tu peux la formuler ainsi:
La validation qualité du preprocessing V2 s’effectue à deux niveaux complémentaires. Le premier niveau est statistique: il vérifie la cohérence des distributions produites par les heuristiques d’enrichissement, notamment sur les champs layer, severity, issue_kind, file_type, board et component. Le second niveau est informationnel: il repose sur des tests de recherche TF-IDF qui servent de proxy simple pour mesurer si les documents prétraités sont déjà récupérables de manière pertinente avant l’intégration dans un véritable pipeline RAG avec embeddings et base vectorielle.

Les scripts statistiques permettent d’identifier rapidement les déséquilibres ou biais des heuristiques. Les scripts TF-IDF permettent quant à eux de vérifier que le signal lexical important est conservé dans les documents après nettoyage et enrichissement. Ensemble, ces validations apportent une preuve intermédiaire que les artefacts docs_issues_v2 et docs_files_v2 sont suffisamment propres, structurés et informatifs pour constituer une base d’ingestion crédible pour un système RAG.

Recommandation pratique pour ST RAG
Si ST chunk lui-même:
passe les documents V2, pas les chunks;
filtre de préférence sur is_valid = true;

utilise clean_text comme contenu source principal.

docs_files_stm32cubeh7_v2.json
docs_issues_stm32cubeh5_v2.json
docs_files_stm32cubeh7_v2.json
