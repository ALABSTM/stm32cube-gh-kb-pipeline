\chapter{Introduction Générale}
%% ============================================================

\section{Contexte}

STMicroelectronics est un leader mondial dans la conception de semi-conducteurs. La famille STM32 représente plus de 1500 références de microcontrôleurs utilisés dans l'industrie, l'automobile, l'IoT et l'électronique grand public.

Les dépôts GitHub publics de STMicroelectronics (\texttt{github.com/STMicroelectronics}) contiennent :
\begin{itemize}
  \item Des paquets logiciels complets (HAL, BSP, Middleware)
  \item Des milliers d'issues et pull requests (retours utilisateurs, corrections de bugs)
  \item De la documentation technique (Release Notes, exemples de code)
\end{itemize}

\section{Problématique}

Les ingénieurs et clients rencontrant des problèmes avec les microcontrôleurs STM32 n'ont pas de moyen efficace d'exploiter la richesse de ces données GitHub. La recherche manuelle dans les issues et la documentation est :
\begin{itemize}
  \item \textbf{Lente} --- des milliers d'issues par série MCU
  \item \textbf{Bruitée} --- contenu non structuré, images, discussions hors-sujet
  \item \textbf{Fragmentée} --- corrélations entre issues/PRs/commits non visibles
\end{itemize}

\section{Objectifs du Projet}

Concevoir et implémenter un pipeline automatisé de prétraitement qui :
\begin{enumerate}
  \item Ingère les données brutes depuis l'API GitHub
  \item Nettoie, enrichit et structure les documents
  \item Génère des artefacts RAG-ready pour une base de connaissances
  \item Alimente un chatbot IA spécialisé STM32 via l'API ST AI Bridge
\end{enumerate}

\section{Plan du Rapport}

\begin{itemize}
  \item \textbf{Chapitre 2} --- État de l'art : RAG, NLP pour code, chatbots techniques
  \item \textbf{Chapitre 3} --- Méthodologie et architecture du pipeline
  \item \textbf{Chapitre 4} --- Implémentation détaillée
  \item \textbf{Chapitre 5} --- Résultats et évaluation
  \item \textbf{Chapitre 6} --- Conclusion et perspectives
\end{itemize}

\chapter{État de l'Art}
%% ============================================================

\section{Retrieval-Augmented Generation (RAG)}

Le paradigme RAG combine la recherche d'information avec la génération de texte par des LLMs \cite{lewis2020rag}. Au lieu de se fier uniquement aux connaissances paramétrisées du modèle, RAG :
\begin{enumerate}
  \item \textbf{Récupère} des documents pertinents depuis une base de connaissances
  \item \textbf{Augmente} le contexte du prompt avec ces documents
  \item \textbf{Génère} une réponse fondée sur des preuves factuelles
\end{enumerate}

\subsection{Avantages pour le domaine technique}
\begin{itemize}
  \item Réduction des hallucinations grâce aux sources vérifiables
  \item Mise à jour continue de la KB sans ré-entraînement
  \item Traçabilité des réponses vers les issues/PRs source
\end{itemize}

\section{Prétraitement pour Knowledge Bases}

La qualité du RAG dépend directement de la qualité des documents indexés :

\subsection{Chunking Strategies}
\begin{itemize}
  \item \textbf{Fixed-size} : simple mais coupe le contexte
  \item \textbf{Paragraph-based} : respecte les frontières sémantiques
  \item \textbf{Section-based} : adapté aux documents structurés
  \item \textbf{Overlap} : assure la continuité contextuelle entre chunks
\end{itemize}

\subsection{Enrichissement Métadonnées}
L'ajout de métadonnées structurées (composant, couche, sévérité) permet un filtrage précis lors de la recherche.

\section{Traitement du Langage Naturel pour Code Source}

\begin{itemize}
  \item TF-IDF pour la similarité inter-issues
  \item Heuristiques regex pour la détection de composants matériels
  \item Classification supervisée vs. règles pour le type de problème
\end{itemize}

\section{Solutions Existantes}

\begin{longtable}{p{4cm}p{5cm}p{4cm}}
\toprule
\textbf{Solution} & \textbf{Forces} & \textbf{Limites} \\
\midrule
GitHub Copilot & Code completion & Pas de KB custom \\
Stack Overflow Search & Communauté large & Pas spécifique ST \\
RAG générique & Flexible & Pas de prétraitement domain-aware \\
\textbf{Notre approche} & Domain-specific + enrichi & Requiert pipeline custom \\
\bottomrule
\end{longtable}

\section{Approche Méthodologique}

Le projet suit une approche itérative :
\begin{enumerate}
  \item \textbf{Phase 1} : Pipeline H7 (série pilote, 12 repos)
  \item \textbf{Phase 2} : Extension multi-séries (F4, H5, U5, WL)
  \item \textbf{Phase 3} : Enrichissement IA (Alfred Vision) et évaluation
\end{enumerate}

\section{Architecture Globale}

Le système s'articule autour de 3 couches :

\begin{enumerate}
  \item \textbf{Couche Data} : ingestion et stockage structuré (JSON)
  \item \textbf{Couche Processing} : pipeline Python en 7 étapes
  \item \textbf{Couche Delivery} : export et upload vers la KB cloud
\end{enumerate}

\section{Choix Techniques}

\begin{longtable}{p{4cm}p{9cm}}
\toprule
\textbf{Choix} & \textbf{Justification} \\
\midrule
Python 3.14 & Écosystème riche (requests, scikit-learn), déploiement simple \\
JSON comme format pivot & Natif pour APIs REST, lisible, versionnable \\
TF-IDF (scikit-learn) & Léger, rapide, suffisant pour la similarité textuelle \\
Heuristiques vs ML & Déterministe, explicable, pas de données d'entraînement requises \\
Architecture modulaire & Chaque étape est rejouable indépendamment \\
\bottomrule
\end{longtable}

\chapter{Implémentation}
%% ============================================================

\section{Ingestion (Stage 1)}

\subsection{Objectif}
Récupérer exhaustivement les données des repositories GitHub configurés.

\subsection{Mécanisme}
\begin{itemize}
  \item Pagination automatique (100 items/page)
  \item Gestion du rate-limiting GitHub (5000 req/h avec token)
  \item Retry exponentiel en cas d'erreur réseau
  \item Fetch parallélisable par repository
\end{itemize}

\subsection{Données récupérées}
Pour chaque repo : issues (avec commentaires), PRs, commits, liens croisés, et fichiers source.

\section{Nettoyage (Stage 2)}

\begin{itemize}
  \item Suppression des issues bot/spam
  \item Normalisation des labels GitHub
  \item Extraction du texte utile (suppression des templates vides)
  \item Déduplication par identifiant
\end{itemize}

\section{Enrichissement V2 (Stage 3)}

\subsection{Heuristiques de Classification}

Le module \texttt{stm32cube\_preprocessing\_heuristics.py} applique des règles basées sur :
\begin{itemize}
  \item \textbf{Regex patterns} : détection de séries MCU, composants, boards
  \item \textbf{Analyse des labels} : mapping label→layer (bug→bug\_report, etc.)
  \item \textbf{Scoring pondéré} : longueur du body, présence de code, de logs d'erreur
\end{itemize}

\subsection{Exemple de Classification}

\begin{lstlisting}[language=json]
{
  "issue_number": 42,
  "title": "HAL_SPI_TransmitReceive DMA fails on STM32F446",
  "layer": "HAL",
  "component": "SPI", 
  "board": "NUCLEO-F446RE",
  "issue_kind": "bug_report",
  "severity": "high",
  "evidence_strength": "high"
}
\end{lstlisting}

\section{Similarité (Stage 4)}

\subsection{Algorithme}
\begin{enumerate}
  \item Construction de la matrice TF-IDF sur le corpus (titre + body + commentaires)
  \item Calcul de la similarité cosinus paire-à-paire
  \item Sélection des top-5 voisins (seuil $> 0.3$)
\end{enumerate}

Formule de similarité cosinus :
$$\text{sim}(A, B) = \frac{A \cdot B}{\|A\| \times \|B\|}$$

\section{Chunking V2 (Stage 5)}

Stratégie de découpage :
\begin{itemize}
  \item Issues : chunks par paragraphe, max 512 tokens, overlap 50 tokens
  \item Files : chunks par section (README headers, fonctions C)
\end{itemize}

\section{Delivery (Stage 7)}

\subsection{Resolver Cases}
Générés à partir d'issues fermées avec PRs liées :
\begin{enumerate}
  \item Identification de la chaîne Issue → PR → Commits
  \item Évaluation du \texttt{resolution\_status} (merged\_fix, candidate\_fix, reference\_only)
  \item Construction du texte structuré : Problème → Signal → Évaluation → Preuves
\end{enumerate}

\subsection{Diagnostic Cards}
Cartes de diagnostic structurées pour les problèmes récurrents :
\begin{enumerate}
  \item Sélection des issues à haute valeur diagnostique
  \item Génération : Symptôme → Cause Racine → Résolution → Validation
  \item Alias de requête pour améliorer la récupération
\end{enumerate}

\section{Couverture des Données}

\begin{longtable}{lcccc}
\toprule
\textbf{Série} & \textbf{Repos} & \textbf{Issues} & \textbf{Files} & \textbf{Resolver Cases} \\
\midrule
STM32F4 & 16 & $\sim$800 & $\sim$5400 & $\sim$150 \\
STM32H5 & 6 & $\sim$200 & $\sim$1200 & $\sim$40 \\
STM32U5 & 8 & $\sim$350 & $\sim$2000 & $\sim$70 \\
STM32WL & 5 & $\sim$150 & $\sim$800 & $\sim$30 \\
STM32H7 & 12 & $\sim$500 & $\sim$3000 & $\sim$100 \\
\midrule
\textbf{Total} & \textbf{47} & $\sim$\textbf{2000} & $\sim$\textbf{12400} & $\sim$\textbf{390} \\
\bottomrule
\end{longtable}

\section{Qualité de l'Enrichissement}

Taux d'enrichissement réussi (champ non ``unknown'') :
\begin{itemize}
  \item \textbf{Layer} : $\sim$85\% des issues
  \item \textbf{Component} : $\sim$70\% des issues
  \item \textbf{Board} : $\sim$45\% (dépend de la mention explicite)
  \item \textbf{Severity} : 100\% (toujours calculé)
\end{itemize}

\section{Performance de Recherche}

Tests TF-IDF sur requêtes techniques :
\begin{itemize}
  \item Précision@5 : $\sim$0.72 (issues), $\sim$0.78 (files)
  \item La recherche hybride (semantic + full-text) sur la KB améliore significativement vs. TF-IDF seul
\end{itemize}

\section{Test Suite Qualité (50 Questions)}

Évaluation sur 50 questions réalistes couvrant les 4 séries (F4, H5, U5, WL) :
\begin{itemize}
  \item Questions formulées en langage naturel ``client''
  \item Chaque question inclut contexte board + symptôme technique
  \item Réponse attendue avec ancrage technique vérifiable
\end{itemize}

\chapter{Conclusion et Perspectives}
%% ============================================================

\section{Bilan}

Ce projet a permis de concevoir et déployer un pipeline de prétraitement complet qui :
\begin{itemize}
  \item Transforme des données GitHub brutes en connaissances structurées
  \item Alimente un chatbot IA spécialisé STM32 en production
  \item Couvre 5 séries MCU (47 repositories, $\sim$14400 documents)
  \item Intègre l'enrichissement IA par vision (Alfred)
\end{itemize}

\section{Perspectives}

\begin{enumerate}
  \item \textbf{Extension à d'autres séries} : STM32L4, STM32G4, STM32MP
  \item \textbf{Enrichissement sémantique} : embeddings pré-calculés pour la similarité
  \item \textbf{CI/CD automatisé} : Jenkins pipeline pour mise à jour continue
  \item \textbf{Évaluation automatique} : scoring RAG avec métriques (Faithfulness, Relevance)
  \item \textbf{Multi-langue} : support des issues en chinois/japonais
\end{enumerate}
